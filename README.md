# Curbside: the build kit for Copilot Studio

> This repository is a snapshot of Curbside's code, shared for the department's rebuild. **The build
> kit is in [`copilot-studio/`](copilot-studio/)**: every file named below is in that folder. The app
> itself is `public/` (the phone app), `worker/` (its server on Cloudflare) and `tools/`; the design
> is `docs/spec-curbside.md`.

**Curbside** is a drivers' app for a department that takes people to and from airports (EWR, JFK,
LGA, SWF, HPN, ALB, BDL) and its own sites. Dispatch sends each run as an assignment PDF, around 5 PM
for the next day. Curbside turns that PDF into the run (stops, doors, passengers, flights, phones),
watches the flights, and says what a delay means for the driver: when to be parked, when the last
passenger will be out, when to leave, beside dispatch's own times.

Dispatch's times were worked out when every flight was on time. When a flight moves, dispatch's
numbers are stale, and Curbside is the only thing that knows. That sentence is the product.

Today Curbside runs for one driver on Cloudflare (a phone app, this repository). This folder is
everything needed to **rebuild it in the department's Microsoft 365, for every driver**, with
Copilot Studio, Dataverse and Power Automate. Copilot Studio builds agents, not apps: it cannot
import this repository or run its JavaScript. It reads documents and calls services. So this kit is
the rules, the data design, the test material and the instructions, written for Copilot Studio,
with every number checked against the code (and the parts that can be, generated from it).

## The two rules that are never broken

1. **Curbside converts; it does not plan.** Dispatch owns the run: the stops, their order, the doors,
   the passengers, the times. The app never re-plans, re-orders or suggests. Its own numbers are
   shown **beside** dispatch's, labelled, never in place of them. The **driver** may change anything
   they need, and the change is shown as theirs with dispatch's original kept.
2. **Two clocks at every airport stop: be there for the earliest obligation, leave after the latest
   one** (`rules/two-clocks.md`).

And: **never guess.** A blank flight, an unknown airline, a missing phone stay blank and are said
to be blank.

## How it fits together

```
 dispatch's PDF ──► Import flow ──► ReadSheet (Azure Function, or AI extraction + driver confirms)
                         │
                         ▼
     Dataverse: cs_run (dispatch's copy, never edited) + cs_change (the driver's log)
                         │  rebuilt after every import and change
                         ▼
     shown tables: cs_stop, cs_passenger (with Parked by / Leaving at)
          ▲                      ▲
          │ reads                │ writes statuses, clocks, alerts
   the agent in Teams     Flight checker (every 20 min) ──► flight data service
   (and a Power App,                     │
    if wanted)                           └──► Teams message to the driver
```

Sign-in is Entra (today's list codes go away). Each driver sees their own runs and those they assist
on; dispatch sees all (`data-model.md`, "Roles").

## Build order

Each step has a test that must pass before the next. Use a test environment and made-up data only.

| # | Build | Done when |
|---|---|---|
| 0 | Ask IT (`it-request.md`) | Items 1, 2, 7, 8 answered; 4 and 5 decided either way. |
| 1 | The tables and roles (`data-model.md`) | A test driver can read only their own runs. |
| 2 | Reading sheets: `ReadSheet` in Azure, or a prompt/Extract node given `reading-the-sheet.md` and `assignment.schema.json` | **15 of 15** samples read as `samples/*.json` says (`reading-the-sheet.md`, "Judging a reading"), and the refusals refuse. |
| 3 | The import flow: number, newest print wins, store, rebuild the shown tables, plan the checks | `test-scenarios.md` 1–3. |
| 4 | The agent, read-only: instructions, knowledge, **Get my runs**, **Get run**, **Import a sheet** | `test-set.csv` rows 1–37 pass with the samples imported for a test driver. |
| 5 | The driver's changes: **Change a value**, **Add a passenger**, **Add a stop**, **Mark not happening**, **Undo a change** | `test-scenarios.md` 4–9; rows 38–40. |
| 6 | The flight checker and Teams alerts | `test-scenarios.md` 10–13; every case in `alert-examples.md` gives the same title, lines and priority. |
| 7 | Messages (**Draft a message**) and the retention job | `rules/messages.md` examples; scenario 17. |
| 8 | A pilot: two drivers, beside today's app, two weeks | Every clock and alert the same in both, or the difference explained. |
| 9 | Every driver; a Power App for the itinerary, if wanted | |

## Loading the kit into Copilot Studio

1. **Create the agent** in the department's environment. Name: `Curbside`. Description (up to 1,024
   characters):
   > Curbside helps the department's drivers with the runs dispatch assigns them. It reads dispatch's
   > assignment sheets, answers questions about a run (stops, doors, passengers, flights, phones), says
   > when to be parked and when to leave when flights move, beside dispatch's own times, records the
   > driver's own changes as theirs, and drafts messages to passengers. It never re-plans a run.
2. **Instructions:** paste the block from `agent-instructions.md`.
3. **Knowledge:** Knowledge → Add knowledge → upload the files marked "knowledge" in the table
   above (Markdown uploads as it is; 500 files and 512 MB each are allowed:
   [Learn](https://learn.microsoft.com/en-us/microsoft-copilot-studio/knowledge-add-file-upload)).
   Give each the description from the table: the orchestrator uses descriptions to pick a source.
   **Upload nothing else.** Whatever is uploaded is readable by anyone who chats with the agent: never
   a real sheet, never a run, never a key.
4. **Tools:** one agent flow (or a connector action) per tool named in the instructions, each
   reading or writing Dataverse **with the signed-in driver's own credentials**. With the Azure
   Function, import `connector.swagger.json` as a custom connector first (Tools → Add a tool → REST
   API; set the host to the Function's).
5. **Test:** Evaluation → import `test-set.csv`.
6. **Publish to Teams** for the test group first.

Which harness: the standard harness fits a rule-bound agent like this one. The GitHub Copilot harness
is needed only to read sheets with the Python reader as a skill (`reading-the-sheet.md`, way B).

## What a chat agent will not do that today's app does

- **Work offline.** Airport garages eat signal; the phone app shows the whole run and queues edits
  with no signal. A Teams agent needs a connection.
- **The itinerary at a glance**: the rail of stops, Right Now, the clocks on screen, done stops
  folding away. A Power App over the same tables can.
- **Open WhatsApp with one tap from the passenger's row**; the agent can give the link.
- **Per-device state**: the theme, ticks, the screen kept awake during a run.

## Keeping the kit true

The kit comes from the code; when the code changes, the kit follows:

- `node tools/kit.mjs` rewrites `samples/`, `test-set.csv` and `alert-examples.md` from the app's own
  reader, clocks and alert wording.
- `cd worker && npm test` includes `kit.test.ts`, which fails when those files drift from the code,
  when the numbers in `rules/two-clocks.md` and `rules/flight-checks.md` differ from the constants,
  when a sample breaks `assignment.schema.json`, or when the instructions pass 8,000 characters.

Facts about Copilot Studio were checked on Microsoft Learn on 2026-10-23. It changes fast: check
again before relying on a limit or a price.

## Privacy

No real data is in this folder. The samples are the app's scrubbed test fixtures with made-up names
and `555` numbers. Never put a real sheet in Copilot Studio as knowledge or as a test.
